## 1. Approved Decisions and How They Were Applied

| Decision / safeguard | Implementation |
|---|---|
| D1: optional `user_id` on `/chat`, optional `personalization` in the response, `PERSONAL` intent | `ChatRequest.user_id` (int ≥ 1), `AgentResponse.personalization` (null by default), `UserIntent.PERSONAL` |
| User must exist and have consented | `/chat` returns 404 for an unknown user, before any session state changes. Consent is checked in `PersonalizationEngine.resolve()` |
| D2: no personal data in the LLM prompt | `generate_answer` receives only the query, products, evidence and filters. Tests assert the display name and preferences never appear in its arguments. `PERSONAL` passes the user's message, not the wishlist |
| D3: no preference capture from chat | The agent has no write path to memory. The DB constrains `user_preferences.source` to `'user_explicit'`. A test confirms tables are unchanged after chat turns like "I prefer TrailMaster" |
| D4: no conversation persistence | `conversations` and `messages` are untouched. Sessions stay in memory |
| Consent off by default; without it, ranking identical to Phase 7 | `personalization_consent DEFAULT 0`. Without consent the router makes the exact Phase 7 `retrieve_with_evidence` call. A test asserts identical call arguments and results |
| Hard filters never overridden; bounded, deterministic adjustments | Re-ranking only reorders a pool retrieved under the same `MetadataFilter`. Movement is at most 2·S − 1 = 5 positions (property-tested on 1,200 seeded cases). Ties keep retrieval order |
| Explanations reference real records | Every reason carries `{table, id}`. A test checks each row exists and belongs to the user. Text is generated by code |
| User IDs are not identity | Documented in `privacy.md`, `limitations.md` and `api-documentation.md`. The API-key check is retained on every `/users` endpoint |
| Transactional export and delete | Delete runs in one SAVEPOINT. Rollback, isolation between users, and complete removal are all tested |
| Safe migrations, backup first, tested on copies | Incremental transactional runner; fresh-DB and v1→v2 tests; rollback test; script trial on a temp copy, then the real DB with a backup |
| Phase 6 validation on every answer path | Search, refine and `PERSONAL` (personalised or not) all call `EvidenceValidator.validate_answer`, which is asserted in unit, integration and live tests. `src/evidence/` is unchanged |

## 2. Features

| Feature | What was built |
|---|---|
| F8.1 Schema v2 and migration | `MIGRATIONS[2]`: consent and `updated_at` on `users`; `source` (CHECK-constrained) and `updated_at` on `user_preferences`; new `feedback` table; 2 indexes. Each step runs in its own transaction. `scripts/migrate_db.py` backs up through SQLite's online backup API before migrating. The API never migrates implicitly: on v1 it serves Phase 7 features and returns 503 for personal ones |
| F8.2 Profile and preferences | `PersonalMemoryService` over `SQLitePersonalMemoryRepository` (behind the `PersonalMemoryRepository` Protocol). Five allowed keys with type and range validation; list values trimmed and deduplicated; malformed stored rows ignored |
| F8.3 Wishlist | Add (idempotent), list (newest first), remove; product must exist |
| F8.4 Feedback | One up/down vote per user and product; the latest vote wins |
| F8.5 Personalised ranking | `PersonalizedReranker` and `PersonalizationEngine` with gates: user exists → enabled → consent. Pool of `limit + 2S − 1`, re-rank, cut to `limit`, then the evidence pack is built for the final products |
| F8.6 `PERSONAL` intent | Offline parser and LLM prompt support. The query is built from the 3 most recent saved titles; saved products are excluded; `seed_records` are reported. No user, no consent or an empty wishlist → clarification with no LLM call |
| F8.7 Session boundary | `SessionState.user_id` (a reference only). A session can't switch users (409). Deleting a user removes their sessions |
| F8.8 Export and deletion | `export_user_data` returns all stored records, the schema version and notes. `delete_user_data` is atomic and returns row counts |
| F8.9 API | 14 new `/users` routes. `/chat` gains `user_id` and `personalization`; the error codes 404, 409 and 503 are new |
| F8.10 Docs | See Section 3 |

## 7. Known Limitations

1. **No per-user authentication.** User IDs are guessable integers; the shared API key is the only control. **The existing Docker setup binds `0.0.0.0` and publishes port 8000 with no key by default**, which exposes personal endpoints to the LAN. This is documented, not changed (deployment config is out of Phase 8 scope).
2. **Offline answers remain low-support and not production-ready.** Live personalised search had `support_rate` 0.22 and `PERSONAL` 0.44, both `is_valid: false`; the validator flags them correctly. Validation was not relaxed.
3. **Weak category signal.** With only two categories in the catalogue, "same category as saved" applies broadly; several products carried that reason without moving. The value of personalisation is unmeasured until Phase 10 (variant D vs C).
4. Re-ranking can't surface products outside the retrieval pool. Weights are hand-set.
5. The `min_rating` preference is stored and exported but not used for ranking.
6. No per-session locking for concurrent requests on the same session. Migration backups are not cleaned up automatically and may contain user data.
7. `docs/database-schema.md` still lacks the Phase 1 column reference for the v1 catalogue tables. Phase 8 documented only its own tables and the migration process.
